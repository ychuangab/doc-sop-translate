# SOP 文件翻譯（doc-sop-translate）

上傳中文 SOP（Word），依術語表翻成目標語言，在每段原文下方插入譯文，產出雙語對照文件。
翻譯後由程式做 QA：術語不符的段落自動「定向收尾」，數值、條號遺失或殘留中文則標紅燈。

線上展示：https://doc-sop-translate.vercel.app （可直接按「用範例 SOP 翻譯」；勾選「對照組」可看到 QA 與收尾的效果）

> 原型來自實際工作：把廠區中英雙語 SOP 補上當地員工的語言（尼泊爾文、越南文），已正式交付使用。
> 正式版是 Python 管線，支援 Word 插入、Word 追加譯文章節、Excel 就地替換三種輸出。
> 這個公開版用虛構文件、以 TypeScript 重新實作核心流程，不含任何公司資料或程式碼。

## 流程

```
DOCX ─ ① 抽段配術語 ─ ② 批次翻譯 ─ ③ QA ─┬─ 黃燈（術語不符）─ ④ 定向收尾 ─ 再 QA ─┐
                                        └─ 綠燈／紅燈 ─────────────────────────────┴─ ⑤ 回寫雙語 DOCX
```

1. **抽段配術語**：抽出含中文的段落（含表格儲存格），比對術語表。比對採最長匹配、不重疊，「點檢表」不會同時算成「點檢」。
2. **批次翻譯**：20 段一批，每段帶編號與該段必須使用的術語，模型以 JSON 逐段回傳；漏回的段落單獨補翻。
3. **QA**（`lib/qa.ts`，不經模型）：
   - 術語遵從性：原文命中術語，譯文就必須出現指定譯法。比「已知錯詞沒有再出現」嚴格，沒見過的同義詞和整個漏譯都抓得到。→ 黃燈
   - 數值與條號：原文的數字（忽略千分位）都要出現在譯文。→ 紅燈
   - 殘留中文、譯文重複或長度異常。→ 紅燈
4. **定向收尾**：只把不符的術語改成規定譯法並調整必要文法，其他文字不動。收尾後若引入紅燈（例如數值被改掉），保留原譯文。
5. **回寫**：直接修改 `word/document.xml`，在每段下方插入綠色譯文，沿用段落與文字格式，但移除清單編號，避免編號被重複計數；表格內的譯文仍在原儲存格。

**結構由程式處理，模型只處理文字**：模型看不到 Word 的 XML，也就不會弄壞版面。

## 對照組

勾選「對照組」時，第一輪不把術語放進提示詞，模擬一般機器翻譯。範例 SOP 實測（47 段、術語命中 48 次）：

| 語言 | 第一輪術語遵從 | 收尾後 | 定向修正 |
|---|---|---|---|
| 英文 | 28～35 / 48 | 48 / 48 | 12～15 段 |
| 越南文 | 24～28 / 48 | 48 / 48 | 17～21 段 |

例如「設備保養人員」第一輪譯成 Equipment Maintenance Personnel，收尾後改為術語表規定的 Maintenance Technician，句子其他部分不變。
一般模式（第一輪就帶術語）英文、越南文、泰文都是 48/48、全數綠燈。

## 本機執行

```bash
npm install
cp .env.example .env.local   # 填入 GEMINI_API_KEY
npm run dev                   # http://localhost:3000
npm test                      # 術語比對、QA、Word 回寫的單元測試
npm run sample -- vi --no-hint   # 不開網頁跑範例（語言 en/vi/id/th；--no-hint 為對照組）
```

範例文件與術語表由 `samples-src/` 的腳本產生：中英術語人工訂定，越南文、印尼文、泰文由 Gemini 依英文定稿翻譯後存檔（`lib/glossary.json`）。

## 目錄

```
app/page.tsx                  上傳、設定、進度、逐段對照
app/api/translate/route.ts    NDJSON 串流進度，最後回傳結果與雙語 DOCX
lib/pipeline.ts               流程與統計
lib/docx.ts                   抽段與雙語回寫（JSZip＋xmldom）
lib/glossary.ts               術語最長匹配與遵從性
lib/qa.ts                     QA 規則與紅黃綠燈
lib/translate.ts              翻譯與定向收尾的提示詞；忙碌時重試並改用備援模型
```
